How to investigate a SIEM alert

Your task is not to guess the incident. Use the SIEM to investigate the evidence, then state what the data proves.

Step 1

Read the SIEM introduction

Before touching an alert, know what the fields mean. Every number in this lab is derived from these fields.

The event schema

All three log sources are parsed into one schema, so you can reason across Windows, Linux and firewall telemetry in the same query.

FieldMeaningUse it to answer
@timestampWhen the event happened (UTC)"When did it happen?"
event_typelogon_failure, logon_success, process_create, privilege_escalation, network_connection"Which events occurred?"
hostSystem the event occurred on"Which host was affected?"
userAccount involved (Windows as DOMAIN\user)"Which user was involved?"
src_ipOriginating address"Which source IP was involved?"
dst_ip / portDestination address and port"What was the traffic targeting?"
process.name / command_lineExecuted binary and its arguments"What did it actually run?"
severityParser-assessed event significance"How serious is this event on its own?"
raw_eventThe original, unparsed log line"What does the source system actually say?"

The three correlation rules

brute_force

Trigger: ≥5 logon_failure from one src_ip within 5 minutes.
Severity: high.
Suppressed if a success from that IP follows, because rule 2 takes over.

successful_brute_force

Trigger: the rule 1 condition plus a logon_success from the same IP and user within 10 minutes.
Severity: critical.

suspicious_process_post_login

Trigger: logon_success followed within 2 minutes by a suspicious process on the same host.
Severity: high.

Triage is a judgement, not a filter

Not everything suspicious alerts, and not everything benign is quiet. One account in this lab fails four logons and then logs in successfully — below the threshold of five, so no alert. Another launches PowerShell 30 minutes after login — outside the 2-minute window, so no alert. Knowing why something did not alert is as important as knowing why it did.

Step 2

Open the SOC Triage Board

Start with the alert population, not with a single alert. You should be able to state how many alerts exist and how they split by severity before you investigate any of them.

Open the SOC Triage Board

What is on the board

  • Alert count by severity (bar chart)
  • Alert timeline over time, split by severity
  • Top source IPs by alert count
  • Suspicious hosts by alert count

Time range matters

The board defaults to the last 7 days. If a panel looks empty, check the time picker in the top right and widen it. All lab alerts fall inside that window.

Steps 3 to 7

The investigation loop

  1. Pick the alert your scenario describesUse severity and the reasoning text to match the brief to a real alert.
  2. Read the alert, not just the titlerule_name, severity, src_ip, user, host, first_seen, last_seen, and the reasoning sentence that states the rule and the numbers.
  3. Follow the evidenceevidence_event_ids lists the exact events behind the alert. In Discover, search by _id to load them, or filter on src_ip / host and the time window.
  4. Read the raw linesraw_event holds the untouched sshd, Windows or firewall line. It is the ground truth for what the source system recorded.
  5. Widen the search for contextLook around the window. What else touched that host or user? Is there a success, a process, or a firewall block that changes the meaning?
  6. Answer each question with a recordType the value and, where it matters, the evidence that proves it.
  7. Write the findingState the security conclusion the evidence supports, and the severity you would assign as the responding analyst.

Nine things every investigation must identify

#QuestionWhere to look
1What happened?Alert rule_name + reasoning
2When did it happen?timestamp, first_seen, last_seen
3Which host was affected?host
4Which user was involved?user
5Which source IP was involved?src_ip
6Which events occurred?event_type across the evidence set
7Why did the SIEM generate the alert?Rule trigger and its thresholds
8What evidence supports your conclusion?evidence_event_ids + raw_event
9What is the final security finding?Your own conclusion, written plainly
Do not guess

If a question asks for a count, a time or an address, find the record. "Probably about five" is not an answer; "10 failed logons, 07:25:55Z to 07:28:07Z" is. A security finding that is not backed by evidence is worthless in a real incident, and that is exactly what this lab is teaching.

Reference

Useful Discover queries

Type these in the Kibana Discover search bar with the normalized-events-* data view selected.

All events from one source IP

src_ip: "203.0.113.45"

All failed logons on one host, newest first

host: "web-01" AND event_type: "logon_failure"

Logons for one account

user: "alice" AND event_type: ("logon_success" OR "logon_failure")

Process creation and privilege escalation

event_type: ("process_create" OR "privilege_escalation")

Find a specific alert's evidence events

_id: ("PASTE_EVIDENCE_ID_HERE")

Firewall blocks toward a host

event_type: "network_connection" AND dst_ip: "10.0.0.10"

High and critical alerts only

severity: ("high" OR "critical")
Tip: the time picker is part of the question

When a question asks "how many", make sure your time range is wide enough to contain the whole sequence. A count taken over four minutes instead of six will be wrong.

Step 4

Working a scenario, end to end

Your answers stay in this browser, so you can leave a scenario half-finished and come back to it. The lab checks what it can check for you.

  1. Read the briefThe incident, the objective, and what you already know.
  2. Investigate in KibanaFind the alert on the SOC Triage Board, then pull its evidence with evidence_event_ids.
  3. Fill in every answer boxType what you found, with the evidence that proves it.
  4. Choose Check answersThe lab grades every fact it can verify, marks each question Correct, Partially correct or Needs work, and for anything unmatched shows which part of the question missed and a hint. It never shows you the answer.
  5. Fix and retryCorrect what the hints point at and check again, as often as you like.
  6. Review your written answersThe interpretation and finding questions are graded by you, not the lab. Tick the box beside each one once you are happy with it.
  7. Mark the scenario completeThis unlocks only once every checkable answer is correct.
If you are completely stuck

Each question has a Show solution link. It gives you the model answer and marks the scenario as assisted, so use it as a last resort — and mention it when you hand your work in.
