Investigation method

The one reference for this lab. Read it once, then work the scenarios.

Lab 07

What this lab is

A complete SIEM pipeline runs locally. Linux, Windows and firewall logs are parsed into one schema, indexed into Elasticsearch, and correlated by three detection rules every 60 seconds. The result is a triage board of alerts, each carrying the evidence that produced it.

For each scenario you take one alert and establish the source IP, the account, the host, the timeline and the raw events behind it — then state a finding the evidence actually supports.

50 normalized events · 3 correlation rules · 4 alerts · 5 scenarios.

Three terms you need

TermMeaning
EventOne recorded security activity, stored as a normalized-events-* document. A single failed SSH login is one event.
AlertWhat a rule raises when it sees a suspicious pattern across several events. No single event produces an alert.
CorrelationConnecting related events to see the story none shows alone. Failures plus a later success mean something different from either part.

Where the evidence lives

  • security-alerts-* — correlation results
  • normalized-events-* — parsed events
  • raw_event — the original, unparsed log line on every event
Method

The investigation loop

Every scenario is a variation on these six steps.

  1. Pick the alert your brief describesMatch on severity and the reasoning text, not the rule name alone.
  2. Read the alertrule_name says which rule fired; severity, src_ip, user, host and first_seen/last_seen give the scope and the window. The reasoning sentence states the numbers behind the decision — read it, then verify every number yourself.
  3. Follow the evidenceevidence_event_ids lists the exact events the alert was built from. Look them up in Discover by _id, or filter on src_ip, host and the window.
  4. Read the raw linesraw_event is the untouched source log line — the ground truth for what the system recorded.
  5. Widen for contextIs there a success, a process or a firewall block around the window that changes the meaning?
  6. Write the findingState the conclusion the evidence supports, and the severity you would assign as the responding analyst.

The chain those steps walk is short: alert → evidence_event_ids → normalized event → raw_event → finding. That link is the whole job.

Do not guess

The SOC Triage Board and Discover are your only evidence source. If a question asks for a count, a time or an address, find the record. "Probably about five" is not an answer; "<COUNT> logon failures from <SOURCE_IP> between <HH:MM:SS>Z and <HH:MM:SS>Z" is, once you have filled it in from the evidence.

An alert is a claim, not proof. Open the events and confirm it. If the alert's numbers and the events disagree, trust the events and say so.

Nine things every investigation must identify

#QuestionWhere to look
1What happened?Alert rule_name + reasoning
2When did it happen?timestamp, first_seen, last_seen
3Which host was affected?host
4Which user was involved?user
5Which source IP was involved?src_ip
6Which events occurred?event_type across the evidence set
7Why did the SIEM generate the alert?Rule trigger and its thresholds
8What evidence supports your conclusion?evidence_event_ids + raw_event
9What is the final security finding?Your own conclusion, written plainly

This is an investigation framework, not a question count. Scenarios 1 to 4 ask you to cover these nine points. Scenario 5 adds a tenth: the handover summary you would give the next analyst.

How you are graded

Every fact the lab can verify is marked Correct, Partially correct or Needs work, and anything unmatched shows which part of the question missed plus a hint — never the answer. Interpretation and finding questions are marked Your call; you tick those off yourself. Each question has a Show solution link that gives the model answer and marks the question assisted, so use it as a last resort.

What is on the board

  • Alert Queue — every correlated alert, one row each
  • Alerts by severity
  • Alert timeline, split by severity
  • Alerts by host
  • Authentication activity per day
  • Top source IPs by event volume
  • Event type mix
  • Event volume by host

The four alert panels describe the correlated alerts. The activity panels describe the much larger body of telemetry behind them, so you can tell an unusual day from an ordinary one before you open Discover.

The board defaults to the last 15 days, which covers the whole dataset. If a panel looks empty, widen the time picker. If one shows Could not find the data view: -, tell your instructor.

The time picker is part of the question

When a question asks "how many", make sure your range is wide enough to contain the whole sequence. A count taken over four minutes instead of six will be wrong.

Schema

Common event fields

All three log sources are parsed into one schema, so you can reason across Windows, Linux and firewall telemetry in the same query.

FieldMeaningUse it to answer
@timestampWhen the event happened (UTC)"When did it happen?"
event_typelogon_failure, logon_success, process_create, privilege_escalation, network_connection"Which events occurred?"
hostSystem the event occurred on"Which host was affected?"
userAccount involved (Windows as DOMAIN\user)"Which user was involved?"
src_ipOriginating address"Which source IP was involved?"
dst_ip / portDestination address and port"What was the traffic targeting?"
process.name / command_lineExecuted binary and its arguments"What did it actually run?"
severityParser-assessed event significance"How serious is this event on its own?"
raw_eventThe original, unparsed log line"What does the source system actually say?"
Two different severities

Every event carries a severity assigned by its parser. Every alert carries a severity assigned by the rule that raised it. They are not the same field. A high event — a blocked firewall packet, for example — does not mean an alert was generated. An alert only exists where a correlation rule actually fired.

Useful Discover queries

Type these in the Discover search bar with the normalized-events-* data view selected. Replace each placeholder with a value from the alert you are investigating.

All events from one source IP

src_ip: "<SOURCE_IP>"

All failed logons on one host

host: "<HOST>" AND event_type: "logon_failure"

Logons for one account

user: "<ACCOUNT>" AND event_type: ("logon_success" OR "logon_failure")

Process creation and privilege escalation

event_type: ("process_create" OR "privilege_escalation")

Find a specific alert's evidence events

_id: ("<EVIDENCE_ID>")

Firewall blocks toward a host

event_type: "network_connection" AND dst_ip: "<DESTINATION_IP>"
Detection

The three correlation rules

brute_force

Trigger: ≥5 logon_failure from one src_ip within 5 minutes.
Severity: high.
Suppressed if a success from that same IP turns up inside the detection window, because rule 2 reports that case instead.

successful_brute_force

Trigger: the rule 1 condition plus a logon_success from the same IP and user within 10 minutes.
Severity: critical.

suspicious_process_post_login

Trigger: logon_success followed within 2 minutes by a suspicious process on the same host.
Severity: high.

The thresholds are not hard-coded. They live in config/app-config.yaml under rules:, alongside the process names each rule treats as suspicious or as expected. That file is the authority when a scenario asks why something did or did not alert.

Triage

Why some activity correctly produces no alert

Not everything suspicious alerts, and not everything benign is quiet. Knowing why something did not alert matters as much as knowing why it did, and you will be asked to explain both.

This lab contains both cases. One account fails a few logons and then logs in successfully — fewer failures than the threshold requires, so no alert. One script runs well after someone logs in, outside the correlation window, so no alert. Find them and account for them against the rules.

ConditionWhat the rules do
Fewer failures than the thresholdNo brute_force alert. A burst under min_failures is not an attack by this rule's definition.
Failures spread beyond the windowNo alert. The rule counts events inside time_window_minutes; the same count over a longer period does not qualify.
Failures split across source IPsNo alert. The rule groups by src_ip, so one IP must reach the threshold on its own.
A process on the expected listNo alert. Rule 3 ignores service and shell processes it considers routine after a logon.
