SIEM basics

Four words you need before you start

This is the whole theory for today. Everything else you learn by doing.

01

What is a security event?

One recorded security activity. This lab stores each one as a normalized-events-* document.

For example: SSH login failed for user dpatel. That is a single event.

One event = one observed activity.

02

What is an alert?

An alert is created when the SIEM detects a suspicious pattern across events — not from any single event.

For example: several failed logins from the same source IP in a short window raises a brute force alert.

Alert = a pattern the SIEM decided was worth your attention.

03

What is correlation?

Correlation means connecting several related events to see the bigger security story that no single event shows.

For example: a run of failed logins plus a later successful login from the same address suggests the attack worked.

Events in sequence tell a story. One event alone does not.

04

What is the SOC Triage Board vs Discover?

Two views of the same lab data, and they answer different questions.

SOC Triage Board tells you what was detected. Kibana Discover lets you investigate why it was detected, event by event.

Board = your alert queue. Discover = the evidence behind it.

The core idea of this lab

How an alert connects to the evidence

The alert tells you what the SIEM detected. The underlying events let you prove what happened. That link is the whole job.

  1. 1
    Security alert
    Raised by a correlation rule. Gives you a rule name, a severity, a reasoning sentence and a window.
  2. 2
    Evidence event IDs
    The alert's evidence_event_ids field lists the exact event documents it was built from.
  3. 3
    Normalized events
    Look those IDs up in Discover to read the real events, and widen the time range to see the surrounding activity.
  4. 4
    Raw source evidence
    Each event keeps its untouched raw_event log line, so you can check the SIEM did not misread it.
  5. 5
    SOC finding
    Write what the evidence supports: activity, target, origin, volume, window, outcome and impact.
The alert is a claim, not proof

An alert says the SIEM detected a pattern. It is your job to open the events and confirm it. If the numbers in the alert do not match what you find in Discover, trust the events and say so.

Lab Objective

Work the alert queue like a SOC analyst

What this lab is

A complete SIEM pipeline is running locally: raw authentication, endpoint and firewall logs are parsed into a single schema, stored in Elasticsearch, and correlated by three detection rules. The result is a SOC Triage Board of alerts, each one carrying the evidence that produced it.

What you will do

Pick a scenario, read the incident brief, then investigate inside Kibana. For every alert you must establish the source IP, the user, the host, the timeline, and the raw events involved — and then state a security finding the evidence actually supports.

Scenarios

Where the evidence lives

  • security-alerts-* — correlation results (open in Discover)
  • normalized-events-* — parsed events (open in Discover)
  • raw_event — the original untouched log line on every event

The three detection rules

  • brute_force — ≥5 failed logons, one source IP, 5 minutes → high
  • successful_brute_force — burst plus a success → critical
  • suspicious_process_post_login — login then risky process within 2 minutes → high
Learning Outcomes

What you will learn

Read a SIEM alert

Interpret rule_name, severity, src_ip, user, host, first_seen/last_seen and the alert reasoning.

Follow the evidence

Use evidence_event_ids to jump from an alert to the exact normalized events that triggered it, then to the untouched raw log line.

Correlate a sequence

Reconstruct an attack timeline across event types: failed logon, successful logon, process creation, privilege escalation, and firewall blocks.

Distinguish signal from noise

Explain why some suspicious-looking activity correctly produced no alert. Triage is judgement, not just filtering.

Understand detection rules

See how a threshold rule works: brute force, successful brute force, and suspicious post-login execution — including their tuning parameters.

Write a security finding

State what happened, when, to which host and account, why the SIEM alerted, and what the evidence proves — in plain language an incident responder can act on.

Five practical investigations

Work them in order. Each builds on the detection logic and evidence vocabulary of the one before it. Your answers must be supported by data you find in the SIEM.

Scenario 01 Easy

Brute Force Investigation

A burst of failed SSH logons against the web server. Establish the source IP, the accounts attacked, the exact time window, and the corroborating firewall evidence.

Scenario 02 Medium

Successful Login After Brute Force

The same failure pattern — but this time a login succeeded. Correlate the failures to the success and explain why the severity escalated to critical.

Rule: successful_brute_force Start Investigation
Scenario 03 Medium

Suspicious Post-Login Process Execution

A Windows account authenticated, then launched a command shell seconds later. Measure the gap, read the command line, and explain why it is dangerous.

Linux Privilege Escalation & Reverse Shell

A Linux account logged in over SSH, then used sudo to start an interactive root shell. Separate this from the legitimate sudo activity on the same host.

Basic Instructions

How to run the lab

Your task is not to guess

Do not answer from the scenario title. Every answer you give must be something you found in the SIEM — an alert field, a timestamp, a source IP, a username, a host, an event type, or a raw log line. If you cannot point to the record that proves it, the answer is not finished.

The SIEM dashboard is your only evidence source

Every number in the answer key exists in Kibana right now. If a question asks for a count, a time, or an IP, find it there.
