Scenario 04 Hard Event: privilege_escalation Rule: suspicious_process_post_login

Linux Privilege Escalation & Reverse Shell

A Linux account logged in over SSH, then used sudo to start an interactive root shell. Separate it from the legitimate sudo activity on the same host.

Incident Brief

Objective and background

Security objective

Establish that a low-privilege account escalated to root and launched an interactive shell, and prove the activity is malicious by contrasting it with normal sudo usage recorded on the same host.

Incident story

The web server has several accounts that legitimately use sudo, and the SOC is used to seeing privilege_escalation events that are perfectly normal. A deployment account was provisioned for automated releases. Last night a high-severity alert fired on web-01 and the operations team want to know whether it is a genuine compromise or another false alarm. This is the hardest judgement call in the lab: you must separate malicious sudo use from routine sudo use using evidence, not vibes.

What you know at the start

  • sudo use is logged as event_type: "privilege_escalation".
  • The same host has other sudo events that are not suspicious.
  • Two alerts on the board share the suspicious_process_post_login rule; this one is on the Linux host.

Investigation task

  1. Locate the alertIt is the suspicious_process_post_login alert on web-01.
  2. Read the sudo recordEvery privilege_escalation event carries the full sudo invocation: TTY, working directory, target user and command.
  3. Identify the privilege changeWhich account escalated, and to which account?
  4. Judge the commandDecide whether the requested command is administrative routine or an interactive shell.
  5. Compare with benign sudoFind the other sudo events on this host and explain precisely what makes them different.
  6. State the finding and the impactInterpret what an interactive root shell over SSH means for the host.

                    Progressive Hints

                    Stuck? Reveal one step at a time.

                    Hint 1 — finding the alert

                    Use the "Top Source IPs by Alert Count" panel. The Scenario 03 alert came from a Windows host; this one came from a different source IP and is on web-01. Confirm by reading the alert's reasoning text, which quotes the exact command that was run.

                    Hint 2 — the sudo record structure

                    A sudo log line looks like:

                    sudo: USER : TTY=... ; PWD=... ; USER=root ; COMMAND=...

                    The second USER= is the account being assumed — that is the escalation. Everything after COMMAND= is what was actually executed.

                    Hint 3 — why the shell matters

                    Compare the requested command against a normal administrative command. Think about what changes when a shell is started interactively over an existing remote session: it is the standard way an attacker keeps control after gaining a foothold, and it is not something a scheduled task or a service restart needs.

                    Hint 4 — finding the benign sudo

                    Filter the normalized events:

                    event_type: "privilege_escalation" AND host: "web-01"

                    You should get more than one hit. Sort by @timestamp and compare the process.command_line and severity of each.

                    Hint 5 — what to write down

                    The comparison question is: "what is the single difference that makes one of these two requests malicious?" Answer that first, and the classification follows. Then say what an interactive root shell means: the attacker can now read and modify everything on that host, and can install persistence.
